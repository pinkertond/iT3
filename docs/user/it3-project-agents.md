# Project agents

Open a project from **Workspaces**. A project with one root conversation opens that chat. For a project with several, choose its manager once in **Agents → Manager chat**. The host saves this choice for connected clients. **Start manager chat** opens the project composer. Send the first message to create the conversation.

- **Team** opens beside native chat. Select a direct agent to open its conversation and see the next layer. **Parent** goes up. The working count includes visible descendants at every depth. Conversations waiting for approval or input appear under **Project attention**. A fork is its own conversation.
- **Project → Project permission defaults** opens the project defaults. Auto delegates routine reviews to compatible providers. The native approval card handles requests that still need a person. Machine policy and provider limits apply.
- **Tasks** opens the host’s shared SQLite task ledger. Create a task with the original request, a source reference, and subtasks. **Assign and notify** saves the receiving chat and queues its task ID. The worker reads the brief, claims an attempt, declares its intended files and checkpoints after each subtask. The page shows **saved**, **queued**, and **acknowledged** as distinct states. Use **Retry delivery** if a saved assignment has no queue receipt.
- To recover an interrupted task, open **Tasks → Inspect interrupted work**. The recovery brief records the former turn’s status and the Git-visible files changed since the last claim or checkpoint, including paths outside the intended file list. The timestamp identifies the inspection. A missing baseline is shown as unavailable. Verify the listed changes before checking off any steps.
- For the same checkout, stop the previous turn in its chat and wait for a terminal state. Use **Assign and notify** to give a second chat the next action. iT3 checks the former turn again when the successor claims. When the former turn is busy or its state is unknown, **Recover in a separate worktree** supplies the snapshot to use as its starting point. Select a chat in that project worktree. iT3 checks its files against the source snapshot. Independent tools, ignored files and external effects need separate verification.
- To compare two approaches, select **Compare two attempts** at creation and assign each attempt a separate native worktree chat. Review their checkpoints, verification, changes, and participating chats’ seven-day usage. Choose **Accept this attempt** after both submit. Acceptance records the selection. Integration of its Git changes is a separate operation.
- **Docs** opens the generated project site. On an indexed task choose **Track this task** to reuse its ID and source path. The task page can open current repository contents. Earlier manually assigned conversation references remain available in the project usage view. Braid informed the document format. The running task service belongs to iT3.
- **Usage** opens the project report. Pick a period, optionally narrow it to one conversation and its visible descendants, and group by model, UTC day, conversation or task reference. Compare tasks and models across periods. The task reference groups the entire conversation, so use separate chats when two tasks need separate costs.
- Usage comes from provider history available on this host. A session must match a unique native provider ID. Shared or unmatched records are excluded. The report labels unpriced records and combines provider-reported costs and model-rate estimates. Subscription bills and unobserved work cannot be inferred from this number.

The local desktop and web clients share these views. Each connected host reports its own sessions and project settings.

## Preview the next step

Open **Workspaces → a project → Queue preview**. The first eligible attempt is marked **Next up**. The list covers active projects on the selected host, including those in other workspaces. Click a task title to open its brief. A visible queue refreshes every minute and when the window regains visibility. **Refresh** requests a new evaluation immediately.

1. In **Tasks**, open a ready task and expand **Queue step**. Enter the next action and its completion check. Add prerequisite task IDs from the same project if needed. A prerequisite clears when an operator accepts its result.
2. Choose **Deterministic check** for a step that takes zero model tokens. For an economy or advanced model, estimate input, output and the percentage points the step could consume in each applicable provider window. A daily USD cap also requires a cost estimate.
3. Under **Queue preview → Project queue policy**, set daily budgets, the maximum estimated context per step, a priority, a reserve percentage and allowed models. The budget day begins at midnight UTC. Background steps can use the economy route. Urgent steps can use the reserve. Active projects sharing a recognized provider account protect the largest configured allowance reserve.
4. Expand a row to see its completion check, observed allowance, estimated balance after this one step and reported reset times. Each row is an independent alternative. An unavailable reading, a reading older than ten minutes, or a reset since the last reading holds model work. The project report counts uniquely attributable sessions. An unsettled active attempt can also hold capacity.

The preview reads recorded state and spends zero model tokens. A ready row is a budget and priority decision. A paid step explicitly assigned to Reviewer can run automatically on this host. Other ready rows remain previews.

## Send a task to Reviewer

1. Open a project chat for code review. Choose **Plan** and either **Auto** or **Approval required**. Select the provider instance and model you intend to use for this queue route.
2. Under **Project → Queue preview → Project queue policy**, choose that chat for **Reviewer seat**, set the economy or advanced route and daily limits, then save. Clear the binding to withdraw standing permission for future reviews. Changing the binding directs new work to the new occupant.
3. Under **Tasks**, open a single-attempt task, expand **Queue step**, choose a model route and enter its next action, verification and estimates. Select **Assign to Reviewer automatically when eligible** and save. A scheduled check on the host can advance it while the window is closed. Remove the option before reservation to return the task to manual scheduling.
4. Open the task to see the hold reason, reservation, chat, native run ID, result and accounting. Answer a provider question or stop an active run in the linked chat. The host recovers a lost delivery response by its original message ID. A passing verdict with every subtask checked completes the attempt. A blocked verdict, requested changes, missing output or unfinished subtask leaves the findings for follow-up. Each attempt authorizes one paid review.

The dispatcher checks active project status, the bound chat, permissions, model, dependencies, observed allowance windows and project limits before sending. The task's fresh-context review receives the request, source reference, next step, subtasks and verification. Model actions still use the native provider's permissions. The host reserves the estimated tokens, USD and share of the provider windows. Concurrent managed reviews sharing a project or account wait. Settlement uses the native run's provider turns. Token counts require complete evidence. Dollar values are standard model-rate estimates on measured usage and can differ from a bill. Unknown usage or prices appear as unavailable. The host checks for late accounting evidence and can update a completed attempt after acceptance. Estimated reservations guide admission and cannot cap a provider turn's final spend. Hosts sharing an external subscription keep separate ledgers.

**Project team** lists the seats below the manager. Bind Architect, Designer or Explorer, route a task, inspect handoffs, or transfer a checkpoint to another occupant.
